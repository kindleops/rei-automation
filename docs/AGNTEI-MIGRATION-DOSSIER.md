How to read it:
- **Objects** are what the migration adds or replaces, recorded by applying it on a disposable database.
- **Production overlap** names tables production's web code uses every day that the file alters, indexes, triggers or writes.
- **Locks**: `ALTER TABLE` takes an ACCESS EXCLUSIVE lock for its duration; a non-concurrent `CREATE INDEX` blocks writes to that table while it builds; a new trigger on a busy table adds work to every write. `lock_timeout` makes the migration give up instead of queueing behind traffic.
- **Data** lists every statement that writes, deletes or drops. "none" means the file only creates or replaces definitions.
- **Existing objects or drift** is decided live, read-only, by `review-chain.mjs` on production (applied, partial, absent, superseded, DRIFT).

## Rollback and recovery

- Every link with a rollback file can be reversed in reverse chain order; the migration-test runner proves each rollback restores the exact pre-link schema fingerprint (`scripts/db/run-migration-test.mjs`).
- Before the first apply: a Supabase point-in-time restore marker, or `pg_dump --schema-only` plus a data dump of the schemas the chain touches (`agent`, `action_gateway`, `public` tables listed above).
- A link that fails rolls back on its own (one transaction). A link that applies but misbehaves is reversed with its rollback file, then the review is re-run before anything else.
